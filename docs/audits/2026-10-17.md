## Threat model and boundaries

Relevant inputs include user commands, existing local repository configuration,
file contents, retrieved web snippets, model responses, and session records.
The model cannot directly select tools. The principal protected assets are
workspace containment, reviewed file contents, session integrity, and application
availability. Git mutations are explicitly submitted commands and intentionally
execute without the write/edit preview flow; that documented behavior is not
counted as a vulnerability by itself.

The Git execution finding requires control of local repository configuration.
An ordinary Git clone does not import another repository's local `.git/config`.
Its impact is code execution with the application's existing user privileges,
not demonstrated privilege escalation or a remotely reachable service exploit.

Path validation and prompt delimiters are useful controls, but neither is an
OS sandbox. Concurrent directory substitution remains a conditional filesystem
concern: no outside-workspace escape was reproduced. It is excluded from the
confirmed security count. Source/web text can still influence model answers
and generated content; no autonomous tool takeover was demonstrated.

## Reproduced application security findings

### S1 - High: Git config grammar mismatch permits a clean-filter command

Location: [tools/git.py](../../src/adityacli/tools/git.py), lines 148-156;
execution at lines 223-246. The section test recognizes `filter ` and `merge `
with a literal space. Git also accepts a tab before a quoted subsection name.
Python's `ConfigParser` retains that tab in the section name, so the deny check
misses it. An allowed `git add payload.txt` then invokes the configured filter.

The control case with a space was rejected. The otherwise equivalent tab case
was accepted and executed a benign Python filter that created a marker only
inside its disposable repository. `shell=False` at the parent process does not
prevent Git itself from launching configured programs. Git documents clean
filters as commands executed during check-in preparation.
[Git configuration reference](https://git-scm.com/docs/git-config#Documentation/git-config.txt-filterdriverclean),
[OWASP subprocess guidance](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html).

Recommended approach: obtain canonical keys through Git's own configuration
parser with includes disabled, then enforce explicit configuration policy.
Keep command-specific argument schemas and executable-producing configuration
checks. Add grammar-variant regression cases. For untrusted local repositories,
use an OS sandbox or restrict mutations until repository trust is established;
string normalization alone is not a complete Git sandbox.

### S2 - Medium, conditional: catastrophic backtracking in Python search

Location: [tools/search.py](../../src/adityacli/tools/search.py), lines 107-120.
When ripgrep is unavailable, user regex is compiled with Python `re` and run on
repository lines without an execution deadline. A 37-character nonmatching
payload and `(a+)+$` exceeded a two-second external timeout. The audit harness
killed its own worker; the application has no equivalent protection.

This requires the fallback backend and a pathological regex/input combination.
It can be triggered accidentally or with crafted local inputs. It is not an
unsolicited remote attack endpoint. Moving this work to `asyncio.to_thread`
does not provide a CPU-time limit or reliable cancellation of the regex.
[CWE-1333](https://cwe.mitre.org/data/definitions/1333.html),
[Python thread offloading limits](https://docs.python.org/3.12/library/asyncio-task.html#asyncio.to_thread).

Recommended approach: offer literal search explicitly; use a non-backtracking
engine for supported regex syntax, or run advanced regex in a killable worker
process with time/input limits. Document syntax differences between backends.
Result caps limit displayed output, not matching time.
[RE2's design guarantees](https://github.com/google/re2).

## Reliability and correctness findings

| ID | Priority | Current problem and observed result | Recommended implementation |
| --- | --- | --- | --- |
| R1 | P1 | `session_store.py:142-172` uses `r+b`, seeks to EOF, and writes without a cross-process lock. Injecting a second append after the first writer's seek caused the second record to disappear. A second application can also clear the shared current session on startup. | Acquire a workspace process lock before session initialization, or implement a single session writer. Use locked journal operations and snapshots, or SQLite transactions with an explicit writer policy. Opening in append mode alone does not make recovery, Clear, and multi-event updates transactional. |
| R2 | P1 | `session_store.py:174-178` deletes the current directory before creating its replacement. Injecting a failure in replacement creation left memory intact but removed disk history. | Prepare and durably validate a new session before switching an active pointer, or use a database transaction. Keep the prior generation recoverable until success. |
| R3 | P2 | `session.py:118-122` changes memory before appending to disk. An injected disk error left one active message and zero saved messages. Cache changes have similar multi-step consistency risks. | Persist a complete operation first, then publish it in memory; or roll back consistently. Give file application and journal recording separate, truthful outcomes when a cross-resource transaction is unavailable. |
| R4 | P2 | `overwrite_service.py:62-67` compares the old file and later calls a separate replacement operation. An injected external edit between those steps was overwritten. | Serialize cooperative writers and carry an expected version through the protected apply operation. Strong protection against noncooperating writers requires platform-specific handle/locking design. A hash followed by an unlocked replace retains the race. |
| R5 | P2 | `response_parser.py:90-93` uses `ast.parse` as Python syntax validation. It accepted module-level `return`, `break`, `await`, and `nonlocal`; Python compilation rejected all four. | Use `compile(source, filename, 'exec')` without executing the code; keep additional language-specific validators optional. Compilation still does not prove correct behavior. |
| R6 | P2 | `git.py:178-199,225-246` and ripgrep reads have no total deadline. The UI prevents normal quit while busy (`cli.py:351-355`). Inference has an SDK timeout, but no explicit total workflow deadline or in-progress cancellation control. | Apply an operation deadline around stream reads and process completion, implement cancellation, and terminate/reap child processes and descendants. Keep the existing bounded-output behavior. A timeout applied only after a blocking stdout read is insufficient. |
| R7 | P2 | Generated-size enforcement occurs in `file_manager.py:22`, during confirmation. A five-byte draft under a four-byte policy still reached the proposal/review stage, then failed on apply. Streamed responses also accumulate before application-level byte checks. | Enforce encoded output limits while receiving data and before parsing, archiving, diffing, or rendering. Retain the final write check as defense in depth. |
| R8 | P3 | `ui/diff.py:15-18` discards line terminators. Changing `value = 1` from a newline-terminated file to an unterminated file produced an empty diff. | Preserve final-newline information and display an explicit no-final-newline marker; define newline/encoding policy for Windows writes. |

Python explicitly states that successful AST parsing does not guarantee
compilable source. Subprocess documentation explains timeout cleanup, bounded
streaming tradeoffs, and executable-path resolution. SQLite provides atomic
transactions; WAL still permits only one writer at a time.
[AST documentation](https://docs.python.org/3.12/library/ast.html#ast.parse),
[subprocess documentation](https://docs.python.org/3.12/library/subprocess.html),
[SQLite transactions](https://www.sqlite.org/transactional.html),
[SQLite WAL](https://www.sqlite.org/wal.html).

## Existing algorithms and recommended evolution

There is no single industry-standard algorithm for a terminal assistant.
Established practice is to make state, trust boundaries, resource budgets, and
failure behavior explicit, then choose the simplest implementation that meets
measured requirements. The current modular single-process design is suitable;
microservices, a large agent framework, and a vector database are not necessary
to address the findings.

Let F be workspace files, G Git metadata entries, B searched bytes, H message
count, J journal bytes, L final response length, and C active cached content.
Filesystem costs also depend on directory depth and storage. Bounds below
describe the current algorithms, not measured performance claims.

| Area and relevant code | Current algorithm/logic | Scaling or reliability limit | Recommended pattern |
| --- | --- | --- | --- |
| `core/parser.py`, `tools/registry.py` | Quote-aware lexical parsing, enum validation, dictionary dispatch; parsing is linear in input length, lookup expected O(1). | Rules are distributed across parser, tool, UI help, and docs. | Keep explicit commands; introduce one typed command specification for argument parsing, limits, side effects, and generated help. Avoid natural-language routing as an optimization. |
| `workspace_guard.py`, `path_resolver.py` | Iterative depth-first directory traversal with pruning; filename lookup scans up to O(F). Repeated path resolution/stat checks enforce boundaries. | Repeated scans and platform-dependent traversal order; path checks cannot stop every concurrent filesystem race. | Stable per-directory ordering, bounded ambiguity lists, and a filename/symbol index with freshness checks and a scan fallback. Preserve security validation when adding caches. Use native handles or sandboxing for stronger hostile-workspace guarantees. |
| `tools/search.py` | Filename-first scan, then batched ripgrep or streaming Python regex; caps 50 results and 300 displayed columns. Native scanning is approximately proportional to searched data; Python regex has an exponential worst case. | Often walks the tree twice; native and fallback regex syntax/order differ. | Define literal/regex modes and backend capabilities, reuse a validated file inventory, enforce deadlines, and retain result/byte limits. Add indexes only after measuring repeated-search cost. |
| `session.py:76-106` | Token-weighted recency eviction using insertion-ordered dictionaries and running token totals; oldest entries are removed until the cache fits. | Recency updates on explicit reread/save, not model use; snapshots become stale after external edits; budget is tied to a static default. | Keep the simple weighted cache, make its policy explicit, and validate freshness with metadata/content hashes. Bind the request evidence budget to the selected model while leaving model loading to LM Studio. |
| `context_manager.py`, `token_counter.py`, `prompt_builder.py` | Greedy newest-first history selection; characters/4 estimate; set-based file deduplication; temporary tool instructions. | Full history copying/counting is O(H) per request; token estimates omit actual tokenizer/template costs. | Keep required evidence distinct from optional history, store token costs incrementally, bound active history, and use model-compatible token counting where available. Clearly identify estimates when exact counts are unavailable. |
| `session_store.py` | Append-oriented JSONL event journal, O(J) replay, fsync per event, backward scan for an interrupted tail, atomic metadata replacement. | No writer lock, schema/version enforcement, snapshot compaction, or retention bound; file history accumulates even after cache eviction. | For current scope: single writer, versioned records, schema validation, periodic snapshots and recovery tests. For multiple sessions/processes: SQLite with transactional updates, migrations, and a bounded reader interface. Choose durability policy explicitly. |
| `file_manager.py`, `overwrite_service.py` | Prepare/preview/confirm, original-content comparison, temporary-file write + fsync + atomic rename per target. | Per-file atomicity is not a multi-file transaction or atomic compare-and-swap; replacement metadata/permissions need an explicit policy. | Keep proposal review; fix R4, validate before preview, define metadata preservation, and track recovery for staged multi-file changes if that feature is introduced. |
| `llm/client.py` | Ordered API compatibility fallback, sorted catalog, one completion stream, chunk list + join, disabled SDK retries. | Catalog discovery repeats on every inference; external response shapes are weakly validated; no total response-byte limit. | Typed boundary validation, short-lived catalog caching with explicit refresh/invalidation, total budgets, and cancellation. Retry only classified transient read failures with bounded backoff; never blindly retry side effects. |
| `cli.py:128-138`, `ui/conversation.py` | Append each delta to the growing string and construct Markdown from the entire accumulated prefix. | Reprocessing all prefixes can approach O(L squared); each chunk crosses to the UI synchronously. This is a source-level scaling assessment, not a UI benchmark. | Batch deltas into a bounded queue and refresh at a capped cadence; use chunk buffers, preserve final rendering and scrolling behavior, and virtualize/paginate long transcripts. |
| `tools/git.py` | Subcommand/flag allowlist, local-metadata checks, environment/config overrides, streamed 128 KiB output cap. | Every command scans Git metadata and the working file list; cost grows with G and F. Config parsing differs from Git; no deadline. | Fix S1 first. Use Git-native parsing, command-specific validation, an explicit trust policy and deadlines. Profile metadata checks; cache only with security-relevant invalidation and keep independent sandbox enforcement. |
| `tools/web.py`, provider, prompt files | Up to five provider snippets are wrapped as untrusted text; model summarizes them. Prompt templates use an eight-entry memoization cache. | Count limits do not guarantee byte/time limits; delimiters are guidance, not a trust boundary. | Validate provider records, cap bytes and total time, keep retrieval data separate from action authority, and test prompt injection if adding new external actions. Current fixed prompt memoization is sufficient. |
| `config.py`, `main.py`, packaging | Frozen dataclass configuration and explicit dependency construction. | Source-only settings, inactive compatibility/security flags, broad dependency ranges, no lockfile or CI workflow in this checkout. | Validate settings once at startup, expose supported configuration deliberately, remove/deprecate ineffective flags, add reproducible application/development locks and platform CI. Keep LM Studio loading controls in LM Studio. |

For files, Windows exposes handle-based sharing and reparse-point controls;
selecting a single flag is not a complete race-free path algorithm.
[Microsoft file-opening reference](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea).
For application/development reproducibility, pinned dependencies and hashes are
supported by pip's documented secure-install workflow. Library compatibility
ranges can remain separate from the application's tested lock.
[pip secure installs](https://pip.pypa.io/en/stable/topics/secure-installs/).

## Controls that passed and limits of the conclusion

The existing suite verifies command routing, explicit file confirmation, invalid
paths, link rejection, bounded search output, model selection, incomplete-stream
handling, context deduplication, and supported UI controls. A separate Git staging
probe confirmed that the current `*.sessions` ignore rule excludes the hidden
`.sessions` directory; no session-leak finding is reported. No direct application
use of `eval`, `exec`, pickle deserialization, `shell=True`, or disabled TLS
verification was found in the reviewed production source.

Passing tests do not establish prompt-injection immunity, correctness of generated
code, race-free filesystem isolation, compatibility with every model, or better
performance than another assistant. Long-session load testing and architecture
comparison benchmarks were not performed. The audit is a bounded review with
reproducible findings, not proof that no further defects exist.

## Recommended order

1. Fix the Git configuration bypass and add grammar-variant security tests.
2. Bound regex/subprocess work and implement actual operation cancellation.
3. Establish session ownership and transactional state changes; fix destructive
   Clear and memory/disk disagreement before expanding background automation.
4. Correct Python compilation checks, enforce output limits before review, and
   preserve diff fidelity and optimistic-write conflict handling.
5. Add dependency locks, reviewed tooling updates, and Windows/UNIX CI with real
   link-fixture coverage and disk-failure/concurrency tests.
6. Measure long-session behavior, then optimize Markdown refresh, history
   retention, and repeated workspace scans. Add RAG or new actions after these
   boundaries are reliable.

documentation/change tracking only.
